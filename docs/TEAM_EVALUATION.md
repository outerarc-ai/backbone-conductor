# 团队协作评估

此流程用于评估由**不同自然人**担任协调者、两位成员和审查者时的协作行为。本机、CI、容器及独立进程测试只验证协议和部署行为，不构成真人使用证据。不要把评估记录或令牌提交到本仓库。选用获授权的测试代码仓库与独立协调 checkout；首次使用避免敏感生产仓库。

参加者可以在各自的 Codex 会话中完成操作。安装方法见 [Codex 插件](CODEX_PLUGIN.md)；成员在远端模式下使用受认证 MCP 桥接，审查者使用认证 CLI，分别持有自己的设备、克隆和令牌。Codex 会话本身不证明真人身份，评估标准如下文所述。

## 开始前

1. 记录项目、预定时间窗、参加者的实际职责和目标代码分支。协调者持有独立协调仓库及管理员令牌；Alice、Bob 各自持有单独的代码克隆和自己的成员令牌；Carol 持有审查者令牌且不持有协调仓库写权限。由参加者本人确认角色和设备归属；令牌 principal 或 Git author 字符串本身不能证明真人身份。
2. 按[部署与恢复](OPERATIONS.md)设置私有凭据目录、可信 HTTPS 证书、认证服务和成员 `/mcp`。确认成员不能读协调仓库、服务端凭据目录或别人的令牌；分别把自己的明文令牌放入其设备上的 0600 单链接普通文件。通过可信途径分发令牌，不把令牌写入命令行参数、仓库或共享记录。需要独立元数据分支时，在固定服务端路径创建/附加并显式同步代码与账本分支。
3. 在每位成员的设备上，先运行只读预检。它不需要 DSH 模型或本地协调仓库，不写入账本：

   ```sh
   backbone member-check \
     --mcp-url https://coordinator.example.org:8443/mcp \
     --member alice --token-file /private/path/alice.token
   ```

   自签或私有 CA 可加 `--ca-file /private/path/ca.crt`。Bob 使用自己的姓名和文件。成功响应含 `verified: true`、`member_id` 和工具数 8；失败即停止此成员试用，先修复证书、Host、令牌或服务配置。预检核对官方 MCP 握手、**精确**成员工具范围，以及 `get_my_task` 返回的成员绑定；不会验证设备持有者的自然人身份。Carol 在自己的设备运行 `backbone reviewer --url https://coordinator.example.org:8443 --token-file /private/path/carol.token whoami`，核对 principal 与 reviewer 角色。

## 协作流程

协调者先在目标代码分支的一个已记录 SHA 上建立两份**事前**意图，审查者按实际上下文接受或拒绝；仅对接受的意图由协调者分派给 Alice 和 Bob。两人分别用[远程成员 CLI](OPERATIONS.md#远程成员-cli)或成员 MCP 获取自己的任务，核对约束并开始任务，在自己的克隆中提交并推送功能分支，随后按[独立代码克隆流程](OPERATIONS.md#独立代码克隆的提交与合并)请求协调端安全获取分支并提交固定 SHA 的制品。成员 CLI 无需模型或 MCP 客户端配置。若试用使用 DSH，模型建议仍是建议。

协调者核对推送来源、完整 SHA、制品范围和真实代码审查后，在目标分支执行 Git 合并。Carol 用 `reviewer inspect TASK_ID --full` 查固定制品补丁和合并后的目标差异，必要时另在完整代码 checkout 审阅；只有目标分支真实集成且审查充分，才用**这次** `inspect` 的 `version` 与 `git.target_sha` 运行 `reviewer approve`。如状态或目标 SHA 已变化，重新审查而非复用旧锚点。至少制造一次并发状态变化以观察过期版本拒绝；若有真实冲突，记录谁裁决、依据及结果，不为了演示而把人工造例当成自然产生的冲突。

结束时由协调者核对任务状态、目标树、远端分支、`timeline --http-principal`、`audit verify-snapshot`、完整的 `audit verify-history --all` 及审计签名报告（若已启用签名），并在服务重启后复查快照。Carol 可独立调用 `reviewer audit-snapshot` 与 `reviewer audit-history` 读取服务端报告；这仍依赖服务端，不能证明真人身份或发现已被改写到不可达的历史。签名只能证明配置的 Git 密钥，不证明某个人亲自操作。按[前瞻评测](../evals/PROSPECTIVE_STUDY.md)另行冻结事前样本和预测，再由两位独立审阅者盲标；一般试用成功不能推出冲突检测率。

## 私有评估记录

在私有位置为每次试用保存以下字段，并让参加者各自确认自己实际执行的步骤。记录操作结果与证据引用，不保存 bearer 令牌、模型密钥、私钥或包含这些秘密的原始日志。

| 字段 | 要记录的事实 |
| --- | --- |
| 环境 | 日期、服务版本及 Git 提交、部署模式、HTTPS 主机名、代码仓库与目标分支（可用私有代号） |
| 人员 | 四个角色由谁实际担任、是否不同自然人、各自设备/克隆的隔离方式；不需要在公开材料中暴露身份 |
| 接入 | Alice/Bob 的预检结果、Carol 的 `whoami` 角色、证书与 Host 校验结果；仅保留去秘密的结果 |
| 流程 | 意图/任务 ID、事前代码 SHA、成员制品 SHA、目标合并 SHA、审批使用的账本版本与目标 SHA |
| 并发与恢复 | 状态竞争、过期版本拒绝、冲突裁决、重启前后状态，以及失败步骤与重试 |
| 审查体验 | 每位参与者的实际耗时、卡点、误解、需要的改动与反馈原话（征得同意后记录） |
| 结论 | 哪些步骤实际由真人完成，哪些只在自动化里验证；未完成项、复现条件、下一次试用安排 |

完整评估要求四个角色由实际不同的人独立完成相应步骤，至少两个成员从独立克隆提交真实代码，审查者在真实合并后核对固定补丁并批准，审计和重启后状态可复核，且记录失败与反馈。容器/进程模拟、共用令牌、缺少合并或缺少审查只能记录为部分流程验证。
